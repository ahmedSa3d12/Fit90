# تصميم مطابقة الجداول الشهرية للتغذية مع التدريب الشخصي

التاريخ: 2026-08-19  
الحالة: معتمد تصميميًا من صاحبة المشروع، بانتظار مراجعة ملف المواصفة قبل التنفيذ  
النطاق: لوحة إدارة التغذية وواجهات API الخاصة بتطبيق العميل

## 1. الهدف

تستخدم إدارة التغذية نفس تجربة الجداول الشهرية الموجودة في التدريب الشخصي: إنشاء جدول كمسودة، فتح تقويم الشهر، إضافة فترات الحضور يدويًا أو بتكرار أسبوعي، نشر الجدول، عرضه، ثم أرشفته. يظل اختلاف التغذية الأساسي محفوظًا: الجدول مرتبط بأخصائي التغذية فقط ولا يحدد خدمة؛ يختار العميل الخدمة عند الحجز، وتحدد مدة الخدمة نهاية الموعد والمواعيد التالية المتاحة.

لا تظهر جداول أو مواعيد التغذية للعميل قبل النشر. لا تتغير شاشات أو APIs التدريب الشخصي أو السبا أو الكلاسات.

## 2. قرارات تجربة الاستخدام

### 2.1 لوحة الإدارة — قائمة الجداول الشهرية

تطابق الشاشة الحالية للتدريب الشخصي في الترتيب والتصميم:

- بطاقة «إنشاء جدول شهري» تحتوي على أخصائي التغذية، الشهر، السنة، وزر إنشاء.
- لا يظهر حقل الخدمة في إنشاء جدول التغذية.
- الجدول يبدأ بالحالة `draft`.
- تظهر المسودات في شريط «فتح تقويم جدول» مثل التدريب الشخصي.
- جدول القائمة يعرض: الرقم، أخصائي التغذية، الشهر، إجمالي فترات الحضور، الحالة، والإجراءات.
- الإجراءات: نشر، عرض الجدول، أرشفة، وحذف المسودة.
- لا يمكن نشر جدول بلا فترة حضور واحدة على الأقل.
- لا يمكن تعديل جدول منشور أو مؤرشف؛ التغيير التشغيلي بعد النشر يكون بإلغاء فترة لم تبدأ، وفق قيود الحجوزات.

### 2.2 تقويم الشهر

يستخدم نفس شبكة الأيام ذات السبعة أعمدة الموجودة في التدريب الشخصي:

- الضغط على يوم يفتح نافذة إضافة فترات الحضور.
- كل فترة تحتوي على: من، إلى، تاريخ ووقت فتح الحجز، تاريخ ووقت غلق الحجز.
- لا توجد خدمة ولا سعة ثابتة؛ الأخصائي لا يستقبل حجزين متداخلين.
- يمكن إضافة أكثر من فترة في اليوم نفسه بشرط عدم التداخل.
- خيار «تكرار أسبوعي تلقائي» يطبق الفترات على اليوم نفسه من كل أسبوع داخل الشهر.
- خلية اليوم تعرض عدد فترات الحضور، وتفاصيل العرض تعرض من/إلى وحالة الفترة وعدد الحجوزات الفعلية داخلها.

### 2.3 عرض الجدول المنشور

نافذة «عرض الجدول الشهري» تطابق التدريب الشخصي بصريًا، مع بطاقة معلومات تحتوي على الأخصائي والشهر والحالة بدل الخدمة والمدرب. يعرض كل يوم فترات الحضور، وحالة كل فترة، وعدد الحجوزات، مع عدم عرض خدمة لأن الخدمات تُختار داخل الحجوزات.

### 2.4 إدارة الحجوزات

تبقى شاشة حجوزات التغذية الحالية، مع نفس أسلوب جدول حجوزات التدريب الشخصي، وتعرض خصائص التغذية الإضافية:

- الخدمة المختارة ومدة الخدمة.
- بداية ونهاية الموعد المحسوبتين.
- «من الاشتراك» أو «مدفوع عند الحضور» وقيمة المبلغ المستحق.
- حالات مؤكد، مكتمل، ملغي، وعدم حضور.
- استرجاع حصة عدم الحضور يتطلب سببًا ويظل مسجلًا في الحجز.

## 3. تجربة العميل وتطبيق الموبايل

واجهة التطبيق الفعلية غير موجودة في هذا المستودع؛ ينفذ هذا المشروع عقد API كاملًا يمكن لواجهة التطبيق استخدامه بنفس ترتيب التدريب الشخصي:

1. عرض خدمات التغذية النشطة.
2. اختيار الخدمة؛ تظهر المدة والسعر.
3. عرض أخصائيي التغذية الذين لديهم جدول منشور.
4. اختيار الشهر واليوم من تقويم الجداول المنشورة.
5. عرض المواعيد المتاحة فقط، محسوبة حسب مدة الخدمة والحجوزات القائمة.
6. اختيار الموعد ثم عرض الرصيد: الإجمالي، المستخدم والمحجوز، والمتبقي.
7. إذا لم يوجد رصيد، يظهر بوضوح أن الحجز مدفوع والدفع عند الحضور، ولا يُمنع الحجز.
8. تأكيد الحجز وإظهاره في «حجوزاتي» مع الخدمة والمدة والتغطية والدفع.

التطبيق لا يستقبل `memberId` من العميل؛ يستخرجه السيرفر من توكن العميل. عند حجز الموعد من عميل آخر قبل التأكيد، يعيد السيرفر تعارضًا، وتحدّث الواجهة قائمة المواعيد وتطلب اختيار موعد آخر.

## 4. بنية البيانات

### 4.1 جدول الخطة الشهرية

إضافة `club_provider_monthly_availabilities` بالحقول:

- `id`
- `employee_id` — أخصائي التغذية
- `category` — ثابتة على `nutrition`
- `month`, `year`
- `status` — `draft | published | archived`
- `published_at`
- `created_at`, `updated_at`

القيد الفريد: `employee_id + category + month + year`.

### 4.2 فترات الحضور

إعادة استخدام `club_availability_slots` مع إضافة:

- `monthly_availability_id` كعلاقة اختيارية بالخطة الشهرية الجديدة.
- `booking_start_at`, `booking_end_at`.
- `cancelled_at` و`cancellation_reason` لدعم إلغاء فترة منشورة دون حذف سجلها.

لفترات التغذية تكون القواعد ثابتة:

- `module_type = nutrition`.
- `trainer_id` مطلوب.
- `service_id = null` دائمًا.
- الفترة تنتمي إلى شهر وسنة الخطة نفسها.
- لا تتداخل فترتان غير ملغيتين للأخصائي نفسه في اليوم نفسه.

تبقى حقول وعلاقات الجدول القديمة متوافقة مع الأقسام الأخرى، ولا تتغير طريقة استخدامها.

### 4.3 الحجوزات

يستمر إنشاء سجل `club_schedules` داخليًا لحظة تأكيد حجز التغذية للتوافق مع التقارير والإشعارات الحالية، بينما المرجع التشغيلي لفترة الحضور يُحفظ صراحة في الحجز بإضافة `availability_slot_id`.

تستمر لقطات الحجز الحالية:

- `duration_min_snapshot`
- `price_snapshot`
- `entitlement_key_snapshot`
- `coverage_type`
- `payment_status`
- حقول استرجاع حصة عدم الحضور وسببها وهوية المسؤول

يمنع المفتاح المرجعي حذف فترة حضور لها حجوزات، وتستخدم حالة الإلغاء بدل الحذف بعد النشر.

## 5. دورة حياة الجدول

### Draft

- يمكن إضافة الفترات وتعديلها وحذفها.
- لا يظهر للأخصائيين في API العميل ولا تُقبل الحجوزات منه.

### Published

- يتطلب فترة حضور واحدة على الأقل.
- يظهر للعميل فقط عندما يكون وقت فتح الحجز قد بدأ ولم ينته وقت الغلق.
- لا يسمح بتغيير حدود فترة عليها حجوزات نشطة.
- يمكن إلغاء فترة مستقبلية مع سبب؛ تُلغى حجوزاتها وفق سياسة الإلغاء الحالية وتُرسل الإشعارات المتاحة.

### Archived

- تختفي مواعيده المستقبلية من API العميل.
- يحتفظ بكل الفترات والحجوزات كسجل تاريخي.
- لا يقبل تعديلات أو حجوزات جديدة.

## 6. منطق المواعيد والحجز

- المرشح الأساسي كل 15 دقيقة داخل فترة الحضور، مع إضافة وقت نهاية أي حجز قائم كمرشح.
- يجب أن تتسع مدة الخدمة كاملة داخل الفترة.
- تستخدم الفترات نصف المفتوحة `[start,end)`، لذلك نهاية حجز يمكن أن تكون بداية الحجز التالي.
- يستبعد السيرفر الأيام والأوقات الماضية حسب توقيت القاهرة.
- عند التأكيد يقفل السيرفر فترة الحضور وصف العميل داخل معاملة واحدة، ثم يعيد حساب النشر ونافذة الحجز والتوفر والرصيد.
- لا يقبل السيرفر وقتًا لم يظهر ضمن قائمة المواعيد المتاحة.
- الحجز المغطى يحجز حصة فورًا؛ الحجز غير المغطى يسجل `pay_at_branch / due_at_branch`.
- الإلغاء يحرر الحصة المحجوزة، والإكمال أو عدم الحضور يستهلكها، والاسترجاع الإداري يعيدها مرة واحدة فقط.

## 7. API الإدارة

تضاف مسارات مخصصة تحت `/api/scheduling/provider-monthly-availability`:

- `POST /` إنشاء مسودة.
- `GET /?category=nutrition` قائمة الجداول مع عدد الفترات.
- `GET /:id` تفاصيل وتقويم الجدول.
- `POST /:id/windows` إضافة فترة أو تكرار أسبوعي.
- `PUT /:id/windows/:windowId` تعديل فترة في المسودة.
- `DELETE /:id/windows/:windowId` حذف فترة من المسودة.
- `PATCH /:id/windows/:windowId/cancel` إلغاء فترة منشورة بسبب.
- `PATCH /:id/publish` نشر.
- `PATCH /:id/archive` أرشفة.
- `DELETE /:id` حذف مسودة بلا حجوزات.

تطبق صلاحيات `club.fitness:view/create/update/delete` ونطاق الأخصائي والفرع الموجودين في النظام. تبقى مسارات الجداول والحجوزات القديمة رافضة لقسم التغذية.

## 8. API العميل

تظل القاعدة `/api/mobile/app/nutrition`، مع تعديل المصادر لتقرأ الخطط المنشورة فقط:

- `GET /services`
- `GET /providers`
- `GET /schedule?serviceId=&trainerId=&year=&month=`
- `GET /eligibility?serviceId=&date=`
- `POST /bookings`
- `GET /bookings/my`
- `PATCH /bookings/:id/cancel`

استجابة الجدول تعرض الخطة المنشورة والأيام والفترات والمواعيد المتاحة، وتضم `availabilitySlotId`, `startTime`, `endTime`, `bookingStartAt`, `bookingEndAt`. لا تُرجع الفترات الملغية أو غير المفتوحة كأوقات قابلة للحجز.

## 9. الترحيل والتوافق

- تُنشأ الجداول والحقول الجديدة دون حذف أي بيانات غير غذائية.
- أي فترات تغذية حالية صالحة في `club_availability_slots` تُجمع حسب الأخصائي والشهر في خطط منشورة للحفاظ على ظهورها، ثم ترتبط بالخطة الجديدة.
- الفترات غير الصالحة، مثل فترة تغذية بلا أخصائي أو مرتبطة بخدمة، لا تُنشر وتُسجل للمراجعة بدل تحويلها تلقائيًا.
- تبقى النسخة الاحتياطية الحالية قبل تغييرات التغذية محفوظة.
- لا يُعاد حذف حجوزات الأقسام الأخرى ولا تتغير بنية حجزها.

## 10. معالجة الأخطاء

- تكرار خطة لنفس الأخصائي والشهر: تعارض واضح.
- نشر خطة بلا فترات: رفض مع رسالة عربية.
- فتح/غلق حجز ناقصان أو الغلق بعد بداية الفترة: رفض.
- فترة متداخلة: رفض مع اليوم والفترة المتعارضة.
- تعديل أو حذف فترة منشورة عليها حجز: رفض واستخدام الإلغاء بسبب.
- حجز وقت أُخذ للتو: HTTP 409، تحديث القائمة، ومسح الاختيار القديم.
- عدم وجود رصيد: ليس خطأ؛ يتحول الحجز إلى الدفع عند الحضور.

## 11. الاختبارات ومعايير القبول

### Backend

- إنشاء مسودة ومنع التكرار.
- إنشاء فترات يومية وأسبوعية والتحقق من الشهر.
- منع التداخل والنشر بلا فترات.
- عدم ظهور المسودة أو المؤرشف في API العميل.
- احترام فتح وغلق الحجز.
- حساب 30 و45 دقيقة وتتابع 15:00، 15:30، 16:15.
- منع الوقت الماضي أو غير المعروض.
- حجز آخر حصة بشكل آمن تحت التزامن.
- الدفع عند الحضور عند نفاد الرصيد.
- No Show والاسترجاع مرة واحدة بسبب وهوية مسؤول.
- رفض مسارات التغذية القديمة.
- عدم تغير اختبارات السبا والتدريب الشخصي والكلاسات.

### Frontend

- شاشة التغذية تطابق ترتيب ومكونات التدريب الشخصي بصريًا مع حذف حقل الخدمة والسعة.
- التقويم يعرض الفترات وعددها، والعرض الشهري يعرض الحالة وعدد الحجوزات.
- أزرار النشر والعرض والأرشفة والحذف تتبع حالة الخطة.
- الحجز يختار الخدمة قبل الوقت ويعرض الرصيد أو الدفع عند الحضور.
- تعارض 409 يمسح الموعد ويحدّث القائمة.
- بناء TypeScript/Vite ينجح.

### قبول صاحبة المشروع

- إنشاء جدول أخصائي لشهر كامل بدون اختيار خدمة.
- نشره بنفس خطوات التدريب الشخصي.
- عدم ظهوره للعميل قبل النشر وظهوره بعده.
- حجز InBody 30 دقيقة ثم جلسة 45 دقيقة، وبدء الموعد التالي عند نهاية السابق.
- إتمام حجز بلا رصيد مع إظهار الدفع عند الحضور.
- إدارة الحضور وعدم الحضور والاسترجاع من شاشة الحجوزات.
